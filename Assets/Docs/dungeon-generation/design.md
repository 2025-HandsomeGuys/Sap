# 던전 절차적 생성 — 설계 (스팰렁키 방식)

작성일: 2026-07-24

> ⚠ **§4 템플릿 계약과 §5 경로 생성은 `maze-and-shape-design.md`(2026-08-28)로 대체됐다.**
> 경로 밖 `FILL` 방과 가로 워커는 폐기되고 형태 마스크 + 미로 배선으로 바뀐다.
> 확률 타일(§6)·슬롯(§7)·출력(§10)·에디터 UI(§11)는 이 문서가 계속 유효하다.

방 템플릿을 격자로 조립해 던전 맵을 생성한다. 스팰렁키 1/2의 레벨 생성 방식(방 격자 → 경로 뚫기 → 손으로 만든 템플릿 조립 → 후처리)을 이 프로젝트의 기존 던전 파이프라인 위에 얹는다.

---

## 1. 목표와 범위

**목표** — 던전 맵을 손으로 한 장씩 그리는 대신, 방 템플릿 몇 개로 여러 던전을 뽑아낸다.

**결정된 방향**

| 항목 | 결정 |
|---|---|
| 생성 시점 | **에디터 생성**. 툴에서 뽑아 프리팹으로 저장. 런타임 생성 아님 |
| 진행 방향 | **가로형**. 왼쪽 입구 → 오른쪽 출구 |
| 크기 | 프리셋 파라미터. 기본 격자 8×3 방 = 82×20 타일 (기존 `trap_gauntlet` 30×12보다 큼) |
| 템플릿 저작 | **기존 txt 포맷 확장**. 파일 하나에 방 여러 개 |
| 확률 타일 | **지원**. 같은 템플릿이 매번 다르게 나옴 |
| 함정/보상 | **하이브리드**. 템플릿이 슬롯 위치를 지정, 생성기가 내용을 굴림 |
| 출력물 | **맵 .txt 저장 + 씬 스탬프 원클릭** |

**범위 밖 (하지 않는 것)**

- 런타임 생성 — 지금은 안 한다. 다만 생성기를 순수 C#으로 짜서 나중에 전환할 때 호출부만 바꾸면 되게 한다.
- 점프 도달 가능성 검증 — 물리 시뮬레이션이 필요해 비용 대비 효과가 낮다. 에디터 생성이므로 사람이 눈으로 확인한다.
- 하강형(위→아래) 던전 — 가로형만. 경로 생성기에 방향 파라미터를 두지 않는다(YAGNI).
- 백 레이어 / 서브 챔버 — 스팰렁키 2에는 있지만 이 프로젝트 던전엔 개념이 없다.

## 3. 파이프라인

```
[방 템플릿 .txt]  +  [DungeonGenPresetSO]  +  [시드 int]
                        │
                        ▼
              DungeonGenerator (순수 C#)
                 1. DungeonPathBuilder     → 방 타입 격자
                 2. DungeonRoomComposer    → 템플릿 선택 + 확률 타일 굴림 + 조립
                 3. DungeonRoomFiller      → 슬롯(?/^/%) 채우기          [M2]
                 4. DungeonLinkRemapper    → 링크 ID 전역 유일화          [M2]
                 5. (외곽 벽 링 + 경계 강제 개통)
                 6. DungeonGenValidator    → E→X 연결성 플러드필          [M3]
                        │
                        ▼
                 DungeonMapData
                        │
                        ▼
              DungeonMapWriter → Assets/DungeonMaps/Generated/gen_<seed>.txt
                        │
                        ▼
              DungeonMapImporter (기존) → 씬 스탬프 → 프리팹 저장(수동)
```

### 난수

`System.Random` 인스턴스 하나를 생성 시작 시 시드로 만들어 파이프라인 전체에 **주입**한다. `UnityEngine.Random`은 전역 상태를 건드리므로 쓰지 않는다.

**같은 시드 → 항상 같은 맵**이 보장되어야 "이 시드 좋다"가 성립한다. 각 단계가 난수를 뽑는 순서가 곧 재현성의 근거이므로, 단계 순서를 바꾸면 같은 시드라도 다른 맵이 나온다는 점을 인지할 것.

## 4. 방 템플릿 포맷

### 파일 구조

파일 하나에 방 여러 개. `---` 한 줄로 구분한다.

```
# tileset: cave              ← 파일 메타 (선택, 참고용)

# room: START R
# weight: 1
[TILES]
WWWWWWWWWW
W........W
W.........
W...0.....
W..WWW....
WWWWWWWWWW
[OBJECTS]
..........
..........
..........
..........
..E.......
..........
---
# room: LR
# weight: 3
[TILES]
WWWWWWWWWW
W..000...W
..0....0..
..........
..WWW.WW..
WWWWWWWWWW
[OBJECTS]
..........
..........
..........
....%.....
..?....^..
..........
---
# room: FILL
[TILES]
WWWWWWWWWW
WWW000WWWW
WW00..00WW
WW0....0WW
WWWWWWWWWW
WWWWWWWWWW
[OBJECTS]
..........
..........
..........
..........
..........
..........
```

위 예시에서 `START R`은 오른쪽 면(열 9)의 **행 2·3·4가 `.`로 확정**되어 있고, `LR`은 좌우 면(열 0·9)의 행 2·3·4가 `.`다. 개구부 자리에 확률 타일(`0`/`1`/`2`)을 두면 굴림에 따라 통로가 막힐 수 있으므로 **개구부는 확정 빈칸으로 둔다**.

- `[TILES]`, `[OBJECTS]`는 필수. `[LINKS]`는 선택(생략 시 전부 `.`).
- 모든 방 템플릿은 **프리셋에 지정된 방 크기와 정확히 일치**해야 한다. 다르면 파싱 에러.
- 기존 `DungeonMapParser`의 블록 문법과 동일하다. 파서는 별도지만 문법 감각은 같다.

### `# room:` 헤더 문법

```
# room: <ROLE?> <OPENS?>
```

- `ROLE` — `START` / `END` / `FILL` 중 하나. 생략 시 `Normal`.
- `OPENS` — `L`/`R`/`U`/`D` 문자를 이어 쓴 열림 방향 집합. `FILL`은 생략.

| 예 | 의미 |
|---|---|
| `# room: LR` | 일반 방, 좌우 열림 |
| `# room: LD` | 일반 방, 왼쪽에서 들어와 아래로 |
| `# room: UR` | 일반 방, 위에서 내려와 오른쪽으로 |
| `# room: START R` | 입구 방. `E` 포함. 오른쪽으로 나감 |
| `# room: END L` | 출구 방. `X` 포함. 왼쪽에서 들어옴 |
| `# room: FILL` | 경로 밖 방 |

`# weight: N` — 같은 (ROLE, OPENS) 조합의 템플릿들 사이 추첨 가중치. 생략 시 1.

### 개구부 위치 규약

경계에서 실제로 지나갈 수 있으려면 템플릿의 열린 면이 정해진 위치에 뚫려 있어야 한다. **템플릿 작성 시 이 규약을 지킨다.**

- **좌우 개구부** — 방 하단 기준 위쪽 3행. 방 높이 6이면 **행 2·3·4** (0=맨 위, 5=바닥 벽).
  플레이어가 걸어서 통과하므로 바닥에 붙어 있어야 한다.
- **상하 개구부** — 방 가운데 3열. 방 너비 10이면 **열 4·5·6**.

규약을 어겨도 아래 "경계 강제 개통"이 뚫어주지만, 그러면 통로가 어색한 위치에 생긴다. 규약을 지키는 편이 낫다.

## 5. 경로 생성 (`DungeonPathBuilder`)

격자 `gridW × gridH` (기본 8×3). 출력은 셀마다 `(role, opens)`.

```
1. col = 0, row = rand(0, gridH-1) → 이 셀이 START, opens = R
2. col을 오른쪽으로 진행:
   a. 굴림: horizontalChance(기본 0.6) 확률로 "오른쪽 이동"
      - 오른쪽 이동: 현재 셀에 R 추가, col++, 새 셀에 L 추가
      - 세로 이동: 위/아래 중 격자 안이고 미방문인 쪽 선택
        (양쪽 다 가능하면 랜덤, 둘 다 불가면 강제 오른쪽 이동)
        현재 셀에 U 또는 D 추가, row 이동, 새 셀에 반대 방향 추가
   b. col == gridW-1 도달 시 종료
3. 마지막 셀 → END (오른쪽 이동으로만 도달하므로 opens는 항상 L)
4. 방문하지 않은 셀 전부 → FILL, opens = None
```

`gridWidth`는 최소 2. 1이면 START와 END가 같은 셀이 된다.

**START는 항상 `R`만, END는 항상 `L`만 열린다.** 시작·끝에서 세로 이동을 허용하면 `START RD`, `START RU`, `END LU` … 전용 템플릿을 다 그려야 해서 초기 작업량이 커진다. 나중에 필요하면 확장한다.

세로 이동 시 지나가는 중간 셀은 `LD`, `UR`, `UD` 같은 조합이 된다.

### 5.1 루프 삽입

워커만 쓰면 경로가 **가지 없는 한 줄**이라 선형적으로 느껴진다. 본선을 깐 뒤, 갈라졌다 다시 합류하는 2×2 사이클을 붙인다.

```
전:  … ─ LR ─ LR ─ …        후:  … ─ LRD ─ LRD ─ …
                                      │     │
                                      UR ── LU
```

```
1. 후보 수집: 가로로 인접하고 Opens가 정확히 LR인 본선 두 칸
2. Fisher-Yates 셔플 (격자 순서대로 훑으면 루프가 늘 왼쪽 위에 몰린다)
3. 각 후보에 대해 maxLoops에 닿을 때까지:
   a. 두 칸이 아직 LR인가 (앞선 루프가 LRD로 바꿔놨으면 탈락)
   b. 위 또는 아래 두 칸이 모두 미방문인가
   c. loopChance 굴림 — 자격 검사 뒤에 굴려서 "쓸 수 있는 자리에서의 확률"이 되게 한다
   d. 본선 두 칸에 D(또는 U) 추가 → LRD / LRU
      곁길 두 칸 = UR·LU (또는 RD·LD), Role = Normal, visited 표시
```

**후보를 `Opens == LR`인 칸으로 제한하는 것이 설계의 핵심.** START(`R`)·END(`L`)·꺾임 방(`LD`/`UR`/`UD`…)을 후보에서 빼면 새로 그려야 할 템플릿이 **`LRD`·`LRU` 둘로 끝나고**, 곁길 두 칸은 이미 있는 `UR`/`LU`/`RD`/`LD`를 그대로 재사용한다. `LRUD` 방을 허용하면 템플릿이 또 늘어나므로 이미 루프에 쓰인 칸은 후보에서 제외한다.

`maxLoops <= 0 || loopChance <= 0`이면 rng를 **한 번도 건드리지 않고** 반환한다. 루프를 끄면 예전 시드가 예전 맵 그대로 재현된다.

**루프가 실제로 몇 번 생기는가** — 병목은 `loopChance`가 아니라 **후보 자리 수**다. 시드 2000개 측정:

| 격자 | 루프 생긴 시드 | 평균 루프 | 도달 방 수 (루프 전 → 후) |
|---|---|---|---|
| 4×3 | 36% | 0.36 | 5.0 → 5.7 / 12 |
| 6×3 | 65% | 0.74 | 8.0 → 9.5 / 18 |
| **8×3 (기본)** | **81%** | **1.12** | **11.0 → 13.2 / 24** |
| 10×3 | 89% | 1.42 | 14.0 → 16.9 / 30 |

`gridWidth`가 4면 본선이 4~7칸이라 START·END를 빼면 순수 `LR` 구간이 거의 안 남는다. 루프를 체감하려면 `gridWidth` 6 이상이 필요하다. `loopChance` 기본값이 1.0인 이유도 이것 — 굴림에서 또 깎으면 보이지 않는다.

**`gridHeight`는 3이 상한선에 가깝다.** 워커는 가로 진행 횟수만큼만 움직이므로 세로를 키워도 아래쪽 행을 거의 안 쓴다. 8×4는 8×3 대비 도달 방이 +0.3개(13.2 → 13.5)인데 밀봉 칸이 8개 늘고 맵 높이가 6타일 늘어난다. 루프 발생률은 81%로 동일 — 루프를 좌우하는 건 `gridWidth`지 `gridHeight`가 아니다.

## 6. 방 조립 (`DungeonRoomComposer`)

### 템플릿 선택

1. `(role, opens)`가 **정확히 일치**하는 템플릿들 중 weight 가중 추첨
2. 없으면 **opens가 상위집합**인 템플릿 (필요한 방향을 모두 포함) 중 추첨 — 여분의 개구부는 막힌 방으로 이어지는 벽감이 되므로 치명적이지 않다
3. 그것도 없으면 **빈 방(테두리만 벽) 생성 + 경고**. 경고는 에디터 창에 표시한다

### 확률 타일 해석

`[TILES]`를 스탬프할 때, 프리셋의 확률 테이블에 등록된 심볼을 만나면 굴려서 치환한다.

| 심볼 | 확률 | 적중 | 실패 |
|---|---|---|---|
| `0` | 0.50 | `W` | `.` |
| `1` | 0.25 | `W` | `.` |
| `2` | 0.75 | `W` | `.` |

프리셋에서 `{symbol, chance, onHit, onMiss}` 리스트로 정의하므로 심볼 추가·변경에 코드 수정이 필요 없다.

`[OBJECTS]`에는 확률 테이블을 적용하지 않는다. 오브젝트의 확률은 슬롯(§7)이 담당한다.

### 좌표 변환

```
최종 격자 크기 = (gridW*roomW + 2) × (gridH*roomH + 2)
방 (gr, gc)의 로컬 (r, c) → 최종 (gr*roomH + r + 1, gc*roomW + c + 1)
```
`+1`은 외곽 벽 링. 최종 격자를 벽으로 채운 뒤 방을 찍는다.

### 경계 강제 개통

조립 후, 경로상 **인접한 두 방 사이 경계**에 통로를 확보한다.

- 좌우 인접 — 경계 양쪽 2열 × 규약 행 3칸을 `.`로
- 상하 인접 — 경계 양쪽 2행 × 규약 열 3칸을 `.`로

프리셋의 `forceCarveBoundaries` 플래그로 끌 수 있다. 템플릿이 충분히 다듬어지면 꺼도 된다.

## 7. 슬롯 채우기 (`DungeonRoomFiller`) — 구현됨 (2026-08-28)

`[OBJECTS]`의 슬롯 심볼을 실제 오브젝트 심볼로 치환한다. 슬롯 정의는 프리셋에 둔다.

| 심볼 | 기본 정의 |
|---|---|
| `?` | 바닥 위험 슬롯. `fillChance` 0.6. 후보 `!`(가시) w3 / `f`(화염) w2 / `_`(무너지는 발판) w2 / `C`(압쇄블록) w1 / `w`(바람) w1 |
| `D` | **왼쪽** 벽에 붙는 다트 자리(오른쪽으로 발사). `fillChance` 0.5. 후보 `>` w1 |
| `d` | **오른쪽** 벽에 붙는 다트 자리(왼쪽으로 발사). `fillChance` 0.5. 후보 `<` w1 |
| `%` | 보상 후보 자리. 아래 별도 규칙 |

채우지 못한 슬롯은 `.`로 지운다.

**슬롯 심볼은 타일셋에 매핑된 오브젝트 심볼과 절대 겹치면 안 된다.** 겹치면 템플릿이 직접 놓은
그 오브젝트가 슬롯으로 잡혀 굴림에 덮인다. 처음에 다트 슬롯을 `^`로 잡았다가 그게 이미
점프대(`JumpTrap`)여서 **생성 맵에서 점프대가 통째로 사라졌다.** 이제
`DungeonRoomTemplateAssetTests.Preset_SlotSymbolsDoNotCollideWithTilesetObjects`가 막는다.
후보 심볼이 실제로 타일셋에 있는지도 같이 검사한다(오타는 임포트 때 경고 한 줄로 조용히 넘어간다).

**다트 슬롯이 좌우로 갈린 이유** — 발사 방향이 프리팹 회전(`zRotation`)으로 심볼에 박혀 있어서
(`>` 0° / `<` 180°) 하나의 슬롯으로 뽑으면 오른쪽 벽에 붙은 다트가 벽 속으로 쏜다.
어느 쪽 벽에 붙는지는 템플릿 작성자만 아는 정보라 심볼로 분리하는 게 맞다. 코드 수정은 없다 —
프리셋 `objectSlots`에 항목 하나를 더 둔 것뿐.

### 경로가 의존하는 것은 슬롯에 넣지 않는다 — 점프대 `^`

점프대는 확률로 굴리지 않고 템플릿에 **직접** 놓는다. 위쪽이 열린 방(`UR`/`LU`/`UD`)은
방 높이 6에 점프 도달이 2칸이라 받침 없이는 위 개구부에 닿지 않는다. 여기서 점프대가
빠진 판이 나오면 그 층으로 못 올라간다. 압력판↔문과 같은 원칙이다.

`LRU` 두 방은 `row3`/`row4`에 확정 벽 발판이 있어 점프대 없이 오를 수 있다 — 그래서 안 넣었다.

**벽에 묻힌 슬롯은 굴리기 전에 지운다**(설계에 없던 추가분). 슬롯 자리의 타일이 확률 타일이었고
벽으로 굴렀다면 프리팹이 벽 속에 박혀 보이지도 만져지지도 않는다. 지운 개수는 경고로 보고한다.
템플릿 쪽 예방책은 `DungeonRoomTemplateAssetTests.CaveRooms_SlotsSitOnValidSurfaces`가 강제한다 —
`?`/`%`는 바로 아래가 **확정 벽**, `^`/`v`는 붙을 면이 확정 벽.

### 보상 `%`

맵 전체를 조립한 뒤, 모든 `%` 위치를 모아 그중 `rewardCount`개(기본 3)를 랜덤 선택해 `$`로 확정하고 나머지는 `.`로 지운다. 후보가 `rewardCount`보다 적으면 있는 만큼만 배치하고 경고한다.

**`FILL` 방의 `%`는 후보에서 제외한다.** 경로 밖 방은 사방이 막혀 있어 도달할 수 없다. 스팰렁키에서는 벽을 파서 들어가지만 이 프로젝트의 던전 타일맵은 파괴할 수 없다. 나중에 던전에 파괴 가능한 벽이 생기면 이 규칙을 재검토한다.

### 남은 약점 — `_`(무너지는 발판)이 놀고 있다

`?` 슬롯은 "바로 아래가 확정 벽"인 자리에만 둔다(공중에 뜬 가시를 막으려고). 그런데 무너지는 발판은
**구멍 위에 걸쳐 있어야** 의미가 있다 — 단단한 바닥 위에서 무너져봐야 그 아래 바닥이 나올 뿐이다.
지금은 `?` 후보 w2로 들어가 있어 뽑히긴 하지만 함정 구실을 못 한다.

고치려면 "구멍 위 발판 자리" 슬롯을 하나 더 만들고(아래가 빈칸인 칸에만 두는 규약) `_`를 그쪽으로 옮긴다.
코드 변경 없이 프리셋 항목 + 템플릿 배치만으로 된다.

**인스펙터 조정이 필요한 후보들** — 손맵 주석이 "임포트 후 조정 필요"라고 적어둔 것들이 슬롯 후보에 있다.
생성 맵은 프리팹 기본값 그대로 나온다.

| 심볼 | 조정 | 기본값일 때 |
|---|---|---|
| `w` 바람 | `windLength`(손맵 권장 3~4) | 1 = 한 칸이라 체감이 거의 없다 |
| `C` 압쇄블록 | `dropDistance` | 방 높이 6 기준이면 대체로 무난 |
| `f` 화염 | `zRotation`(0=오른쪽 90=위 180=왼쪽 270=아래) | 타일셋 매핑이 0°(오른쪽) 고정 |

방향·길이까지 굴리려면 슬롯 후보에 회전값을 실어야 하는데, 그건 타일셋 `objectMappings`에
방향별 심볼을 추가하는 쪽이 코드 변경이 없다(`<`가 `>`의 180° 변형인 것과 같은 방식).

### 링크 기믹은 슬롯에 넣지 않는다

압력판 `P` ↔ 문 `G`처럼 **짝이 맞아야 성립하는 기믹은 슬롯 후보에서 제외**한다. 확률로 뽑으면 한쪽만 나오는 사고가 난다. 이런 기믹은 템플릿의 `[OBJECTS]`와 `[LINKS]`에 통째로 직접 작성한다.

## 8. 링크 ID 재배정 (`DungeonLinkRemapper`) — M2

방 템플릿의 `[LINKS]`는 방 안에서만 `1`, `2` … 를 쓴다. 방 A의 `1`과 방 B의 `1`이 조립 후 같은 그룹으로 배선되면 안 된다.

조립할 때 방마다 로컬 링크 문자를 **전역 유일 문자**로 재매핑한다. 풀은 `1-9`, `a-z`, `A-Z` 순서(61개). 고갈되면 이후 링크는 `.`로 지우고 경고한다 — 잘못 배선되느니 링크가 없는 편이 안전하다.

기존 `DungeonMapImporter.WireLinks()`가 이 문자를 그룹 키로 쓰므로, 재매핑만 정확하면 배선은 그대로 동작한다.

## 9. 검증 (`DungeonGenValidator`) — M3

- **연결성** — `E` 위치에서 빈칸(`.`)을 4방향 플러드필해 `X`에 닿는지 확인
- **개수** — `E`와 `X`가 정확히 1개씩인지 (`DungeonMapImporter`도 같은 검사를 하지만 생성 단계에서 먼저 잡는다)

실패 시 시드를 `seed+1`, `seed+2` … 로 바꿔 **최대 20회 재시도**한다. 전부 실패하면 마지막 결과를 반환하되 에디터 창에 실패 표시를 띄운다.

점프 도달 가능성은 검증하지 않는다.

## 10. 출력 (`DungeonMapWriter`)

`DungeonMapData` → 기존 `DungeonMapParser`가 읽을 수 있는 txt.

```
# dungeon: gen_12345
# cell: 1
# size: 42x20
# preset: cave_horizontal
# seed: 12345
[TILES]
...
[OBJECTS]
...
[LINKS]
...
```

저장 위치: `Assets/DungeonMaps/Generated/gen_<seed>.txt`. 같은 이름이 있으면 덮어쓴다(같은 시드 = 같은 맵이므로 무해).

`# preset`·`# seed` 메타는 기존 파서가 무시하지만, 나중에 "이 맵 어디서 나왔지"를 추적할 수 있게 남긴다.

## 11. 에디터 UI (`DungeonMapImporter` 확장)

기존 Import 섹션 위에 Generate 섹션을 추가한다.

```
┌─ Generate ─────────────────────────────┐
│ Preset   [DungeonGenPreset_Cave ▾]     │
│ Seed     [12345]  [🎲 Random]          │
│                                        │
│ ┌─ Preview ────────────────────────┐   │
│ │ WWWWWWWWWWWWWWWWWWWWWWWWWWWWWWWW │   │
│ │ W..E.......W.........W.........W │   │  ← 등폭 폰트 ASCII
│ │ WWWW..WWWWWW..WWWWWWWW..WWWWWWWW │   │     스크롤 가능
│ └──────────────────────────────────┘   │
│                                        │
│ ⚠ 경고 2건: LU 타입 템플릿 없음 …       │
│                                        │
│ [ Generate ]  [ Save Only ]  [ Save & Stamp ] │
└────────────────────────────────────────┘
─────────────────────────────────────────
┌─ Import (기존) ────────────────────────┐
│ Map Root / Tileset / Map(.txt) / Clear │
│ [ Import ]                             │
└────────────────────────────────────────┘
```

**작업 흐름** — 주사위를 눌러 시드를 바꿔가며 ASCII 프리뷰로 골격을 훑는다. 괜찮아 보이면 `Save & Stamp`로 씬에 실제 타일을 찍어 확인한다. `Save & Stamp`는 기존 Import 섹션의 Map Root·Tileset 설정을 그대로 사용한다.

`Generate`는 파일을 쓰지 않고 프리뷰만 갱신한다. 반복이 빨라야 하므로 디스크 접근을 뒤로 미룬다.

## 12. 프리셋 (`DungeonGenPresetSO`)

```
[CreateAssetMenu(menuName = "Dungeon/Generation Preset")]

# 크기
int gridWidth  = 4        # 방 격자 가로
int gridHeight = 3        # 방 격자 세로
int roomWidth  = 10       # 방 하나 가로 (타일)
int roomHeight = 6        # 방 하나 세로 (타일)

# 템플릿
List<TextAsset> roomTemplateFiles

# 경로
float horizontalChance = 0.6f

# 확률 타일
List<ChanceTile> chanceTiles          # { char symbol; float chance; char onHit; char onMiss; }

# 슬롯
List<ObjectSlot> objectSlots          # { char symbol; float fillChance; List<WeightedSymbol> candidates; }
int rewardCount = 3
char rewardSlotSymbol = '%'
char rewardSymbol     = '$'

# 안전망
bool forceCarveBoundaries = true
int  maxRetries = 20
```

기본 크기 4×3 방 × 10×6 타일 = **42×20 타일** (외곽 벽 포함). 기존 `trap_gauntlet`(30×12)보다 크다. 격자 크기는 인스펙터에서 바로 늘려가며 감을 잡는다.

## 13. 구현 순서

### M1 — 지형 뼈대 + 프리뷰 루프

**여기서 "맵 느낌"을 확인하는 것이 이 마일스톤의 목적.** 함정·보상·링크·검증은 전부 뺀다. 확률 타일은 **포함** — 지형 다양성의 핵심이라 이게 없으면 느낌 판단이 안 된다.

| 파일 | 내용 |
|---|---|
| `Generation/DungeonRoomTemplate.cs` | `RoomOpen` 플래그, `RoomRole` 열거형, 템플릿 데이터 |
| `Generation/DungeonRoomTemplateParser.cs` | `---` 구분 + `# room:` 헤더 파싱, 크기 검증 |
| `Generation/DungeonGenPresetSO.cs` | §12 (M1 필드만) |
| `Generation/DungeonPathBuilder.cs` | §5 |
| `Generation/DungeonRoomComposer.cs` | §6 (템플릿 선택 + 확률 타일 + 외곽 벽 + 경계 개통) |
| `Generation/DungeonGenerator.cs` | 오케스트레이터. `Generate(preset, seed)` → `GenerationResult` |
| `Generation/DungeonMapWriter.cs` | §10 |
| `Editor/Dungeon/DungeonMapImporter.cs` | Generate 섹션 추가 (§11) |

**최소 템플릿 세트** — `START R` 1, `END L` 1, `LR` 3, `LD` 1, `UR` 1, `LU` 1, `RD` 1, `UD` 1, `FILL` 2. 약 12개.

### M2 — 함정·보상·링크

`DungeonRoomFiller.cs` (§7), `DungeonLinkRemapper.cs` (§8) 추가 + 프리셋 필드 확장.

- [x] `DungeonRoomFiller.cs` + 프리셋 `objectSlots`/`rewardCount` + `cave_rooms.txt` 슬롯 배치 (2026-08-28)
- [ ] `DungeonLinkRemapper.cs` — 아직. 지금은 템플릿 `[LINKS]`가 전부 비어 있어 충돌이 날 게 없다.
      **템플릿에 압력판·문을 넣는 순간 이게 먼저 필요하다** — 방 A의 `1`과 방 B의 `1`이 한 그룹으로 배선된다.

⚠ 슬롯 단계가 파이프라인에 끼어들면서 **난수 소비 순서가 바뀌었다** — M1에서 뽑아둔 시드는 같은 맵을 재현하지 않는다.
`Assets/DungeonMaps/Generated/`가 비어 있어 실제 피해는 없었다.

### M3 — 안전망

`DungeonGenValidator.cs` (§9) + 재시도 루프 + 에디터 창 경고/실패 표시.

## 14. 테스트

생성기가 순수 C#이므로 EditMode 테스트를 붙인다. **프로젝트 규칙에 따라 테스트 작성만 하고 실행은 사람이 한다.**

| 대상 | 확인 |
|---|---|
| `DungeonRoomTemplateParser` | 여러 방 파싱, 헤더 문법, 크기 불일치 시 에러 |
| `DungeonPathBuilder` | START가 col 0에·END가 col gridW-1에, 경로가 끊기지 않음, opens 대칭(A의 R이면 B의 L) |
| 재현성 | 같은 시드 → 같은 `DungeonMapData` (전 파이프라인) |
| `DungeonRoomComposer` | 좌표 변환, 외곽 벽 링, 정확한 타입 없을 때 폴백 |
| `DungeonLinkRemapper` | 방 간 링크 문자 충돌 없음, 풀 고갈 시 경고 |
| `DungeonGenValidator` | 막힌 맵을 실제로 실패로 잡는지 |
