# 던전 절차 생성 — 미로 배선 + 형태 마스크 설계

작성일: 2026-08-28
선행 문서: `design.md`(스팰렁키 방식 원설계). 이 문서는 그중 **§5 경로 생성**과 **§4 템플릿 계약**을 대체한다.

---

## 1. 왜 바꾸나

첫 생성 결과를 보고 두 가지가 드러났다.

**경로 밖 방(`FILL`)의 빈 공간이 무의미하다.** 스팰렁키는 폭탄으로 벽을 뚫어 그 공간에 들어가지만,
이 프로젝트의 던전 타일맵은 파괴할 수 없다. 그래서 밀봉된 공동은 영원히 못 가는 장식이 된다.
화면상으로는 "암반 한가운데 뚫린 주머니"로 보여 지형이 지저분해 보이기까지 한다.

**던전이 매번 가로로 긴 한 줄이다.** 워커가 왼쪽에서 오른쪽으로 진행하는 구조라 형태가 하나뿐이다.
손으로 만든 `flame_shaft`(24×22 수직 상승)처럼 세로형·꺾인 형태가 나오지 않는다.

### 결정

| 항목 | 결정 |
|---|---|
| 경로 밖 칸 | **미로로 전환.** 던전 칸 전부를 서로 연결해 출구까지 여러 경로가 존재하게 한다 |
| 남는 암반 | **통짜.** 빈 공간을 품지 않는다. 도달 불가 공동은 후처리로 메운다 |
| 던전 형태 | **격자 마스크를 텍스트로 그린다.** 가로·세로·ㄱ자·십자 전부 데이터로 표현, 코드 변경 없음 |
| START/END | **전용 템플릿 폐지.** 생성기가 시작·끝 칸의 바닥에 `E`/`X`를 후처리로 찍는다 |

## 2. 형태 마스크

### 파일 위치와 구조

`Assets/DungeonMaps/Shapes/basic_shapes.txt`. 한 파일에 형태 여러 개, `---` 한 줄로 구분한다
(방 템플릿 파일과 같은 관례).

```
# shape: 가로형
# weight: 3
S.....X
---
# shape: 세로형
S
.
.
.
X
---
# shape: ㄱ자
# weight: 2
S....
.....
..###
....X
```

### 문법

| 문자 | 뜻 |
|---|---|
| `S` | 시작 칸. `E`(입구)가 이 방에 놓인다 |
| `X` | 끝 칸. `X`(출구)가 이 방에 놓인다 |
| `.` | 던전 칸 |
| `#` | 던전 아님 — 통짜 암반 |

- 헤더 `# shape: <이름>`은 경고 메시지용. `# weight: N`은 형태 추첨 가중치(생략 시 1).
- **모든 행의 길이가 같아야 한다.** 다르면 에러 — 짧은 행을 `#`로 패딩하면 의도치 않게 던전이 잘린다.
- `S`와 `X`는 각각 정확히 1개. 알 수 없는 문자는 에러.
- `S`에서 던전 칸만 밟아 4방향으로 `X`에 닿아야 한다. 안 닿으면 에러(형태 자체가 틀린 것이다).
- `S`/`X` 연결 성분 밖에 떨어져 있는 던전 칸은 **암반으로 강등하고 경고**한다. 에러로 막지 않는 이유는
  형태를 손으로 그리다 보면 한 칸 삐져나오는 실수가 잦고, 그 한 칸 때문에 생성이 실패하면 짜증만 나기 때문이다.

### 신규 코드

- `DungeonShapeMask` — 파싱 결과. `char[,] Cells`, `Name`, `Weight`, `StartCell`, `EndCell`.
- `DungeonShapeParser` — `Parse(text, sourceName)` → `Templates`/`Errors`/`Warnings`. 방 템플릿 파서와 같은 형태.

## 3. 미로 배선 (`DungeonPathBuilder` 교체)

기존 워커 + 루프 삽입 코드를 버린다. 가로형은 `S.....X` 마스크 한 줄로 그대로 재현되므로 기능 손실이 없다.

### 알고리즘

1. **랜덤 DFS 스패닝 트리** — `S` 칸에서 출발. 스택 기반, 매 칸에서 아직 방문 안 한 이웃 던전 칸을
   셔플해 하나 고르고, **양쪽 방의 맞닿은 면에 개구부 플래그를 세운다**(A의 `R`이면 B의 `L`).
   막히면 스택을 되감는다. 트리가 완성되면 **모든 던전 칸이 반드시 `S`에서 도달 가능**하다.
2. **추가 연결** — 인접한 두 던전 칸 쌍 중 아직 안 뚫린 면을 전부 모아 셔플하고,
   각각 `extraConnectionChance`(기본 0.25)로 굴려 뚫는다. 이게 순환로와 갈림길을 만든다.

트리가 연결성을 알고리즘 자체로 보장하고, 추가 연결은 그 위에 얹기만 하므로 **고립 방이 원리적으로 없다.**
"뚫고 나서 검사하고 실패하면 재시도"가 필요 없다.

### 출력

`RoomPlan[,]` — 지금과 같다. `Role`만 의미가 바뀐다.

| Role | 뜻 |
|---|---|
| `Normal` | 일반 던전 칸 |
| `Start` / `End` | 던전 칸이면서 `E`/`X`가 놓일 자리. **템플릿 선택에는 더 이상 쓰지 않는다** |
| `Rock` | 마스크 `#` 칸. 방이 아니라 통짜 암반 (기존 `Fill`을 대체) |

`RoomRole.Fill`은 제거한다. "경로 밖의 밀봉된 방"이라는 개념이 사라졌으므로 이름이 거짓이 된다.

## 4. 방 템플릿 계약

### 개구부 15종 전부 필요

미로에서는 어떤 조합이든 나올 수 있다.

```
L    R    U    D          막다른 방 4종
LR   LU   LD   RU   RD   UD     2방향 6종
LRU  LRD  LUD  RUD              3방향 4종
LRUD                            4방향 1종
```

자주 나오는 조합(`LR`, `UD`, `LRU`, `LRD`)은 2~3장씩 두고 나머지는 1장으로 시작한다. 총 20장 안팎.

### START/END 전용 템플릿 폐지

미로에서는 시작 칸의 개구부 조합을 미리 알 수 없다. 전용 템플릿을 유지하면
`START LRUD`까지 15종 × 2를 더 그려야 한다. 대신 생성기가 후처리로 찍는다(§5).

### FILL 방 폐지

암반 칸은 템플릿 없이 통짜 벽으로 채운다. 조립기가 최종 격자를 벽으로 초기화한 뒤 던전 칸에만 방을
찍으므로, 암반 칸은 **아무것도 안 하면 그대로 통짜 벽**이 된다.

이로써 `# room:` 헤더의 ROLE 표기(`START`/`END`/`FILL`)는 전부 쓰이지 않는다. 템플릿은 개구부 조합만
선언하고, 파서는 ROLE이 붙어 있으면 경고 후 무시한다(구 템플릿을 열었을 때 조용히 깨지지 않도록).

### 그대로 가는 것

**개구부 위치 규약**(원설계 §4)은 유지한다 — 좌우는 행 2·3·4, 상하는 열 4·5·6, 그 자리에 확률 타일 금지.
방 크기 10×6도 그대로다. 경계 강제 개통(`forceCarveBoundaries`)도 유지하며, 미로에서는 뚫어야 할
경계가 훨씬 많아지므로 오히려 더 중요해진다.

### 세로 이동 규약 — 발판 사다리 (2026-08-29 개정)

**`U`가 열린 방은 개구부 열(4·5·6) 안에 발판 사다리를 둔다.**

| 위치 | 역할 |
|---|---|
| 행 3 · 열 4 에 `W` 한 칸 | 바닥(행 4)에 선 플레이어가 옆칸에서 뛰어올라 **발판 위(행 2)** 에 선다 |
| 행 1 · 열 6 에 `W` 한 칸 | 행 2에서 뛰어올라 **발판 위(행 0 = U 개구부)** 에 선다. 거기서 윗방으로 이어진다 |

- **두 발판은 열이 달라야 한다.** 같은 열에 수직으로 겹치면 머리가 막혀 두 번째 점프가 죽는다.
- 사이 통로(행 3·2·1의 열 5, 행 2의 열 4)는 **확정 `.`** 으로 비워 둔다. 확률 타일도 두지 않는다 —
  굴림 한 번에 사다리가 끊긴다.
- 기하 근거: 플레이어 수직 점프 도달은 **2칸**(행 R → 행 R-2). 이 프로젝트 손맵의 공통 규약이고
  `flame_shaft.txt`(선반 수직 간격 2칸)·`jump_basic.txt`가 그 값으로 만들어져 있다.
- `DungeonRoomTemplateAssetTests.CaveRooms_UpOpenRoomsAreClimbable`이 강제한다 —
  "`U`가 열린 모든 방에 대해 열 4~6 안에 행 3의 `W`가 하나 이상, 행 1의 `W`가 하나 이상".

#### 왜 점프대 규약을 폐기했나 — 검증 가능한 틀린 규칙

이전 판은 "**`U`가 열린 방은 점프대(`^`)를 하나 이상 둔다**"였다. 발판으로 오를 수 있는지는
물리 시뮬레이션 없이 판정할 수 없다고 보고, 검사하기 쉬운 쪽(`^`의 존재)으로 규칙을 바꾼 것이다.

그 규칙은 **틀렸다.** `Assets/DungeonMaps/flame_shaft.txt:23`에 이 저장소 자신의 측정치가 남아 있다 —
**"`^` 점프대는 약 2.94칸까지만 오른다."** 방은 10×6이고 바닥은 행 4, 천장 개구부는 행 0이라 **4칸**이다.
점프대로는 천장에 손이 닿지도 않는다. 게다가 당시 9장 중 5장은 점프대가 개구부 열(4~6) 밖에 있어
시도조차 못 했고, `LRUD`는 점프대 바로 위 행 3이 `W`라 1칸 굴에 갇혀 있었다.

결과는 **조용한 클리어 불가 맵**이었다. 공동 메우기는 4방향 연결만 보므로 통과하고, 생성기는 성공을 보고한다.
테스트는 초록불이었다. **검증 가능하지만 틀린 규칙이, 검증 불가능하지만 옳은 규칙을 밀어낸 것이다.**

발판 사다리는 그 딜레마를 없앤다 — `flame_shaft`가 이미 쓰는 관용구(수직 2칸 간격 선반)라
프리팹 튜닝을 건드리지 않고, "개구부 열에 2칸 간격으로 발판이 있는가"는 물리 시뮬레이션 없이 검사된다.
점프대는 없애지 않았지만 **오르는 수단이 아니라 연출**로 격하됐다.

교훈: 규칙을 테스트하기 쉬운 형태로 바꿀 때는, 바뀐 규칙이 원래 요구를 여전히 함의하는지 먼저 확인한다.
못 하겠으면 규칙을 약화시키지 말고 **검사 방법을 바꿀 수 있게 설계를 바꾼다**(여기서는 관용구 자체를 교체했다).

## 5. 파이프라인

```
마스크 선택 → 미로 배선 → 방 조립 → E/X 배치 → 공동 메우기 → 슬롯 채우기
```

순서에 이유가 있다.

- **E/X 배치가 공동 메우기보다 먼저** — 플러드필의 출발점이 `E`다.
- **슬롯 채우기가 마지막** — 메워진 칸에 슬롯이 있어도 기존 "벽에 묻힌 슬롯 삭제"가 알아서 지운다.
  순서를 뒤집으면 프리팹이 벽 속에 박힌다.

### E/X 배치 (`DungeonEntryPlacer`)

시작 칸의 방 영역에서 **바닥 빈칸**(타일이 `.`이고 바로 아래가 `W`)을 모아 rng로 하나 골라 `E`를 찍는다.
끝 칸도 같은 방식으로 `X`.

- 슬롯 심볼이 이미 있는 칸은 후보에서 뺀다(슬롯을 덮어 없애지 않도록). 후보가 그것뿐이면 덮어쓴다.
- 바닥 빈칸이 하나도 없으면 그 방 맨 아래 행 가운데를 뚫어 바닥을 만들고 그 위에 놓는다 + 경고.
  실패로 처리하지 않는 이유는 `E`가 없는 맵은 임포트 자체가 무의미하기 때문이다.

### 공동 메우기 (`DungeonCavityFiller`)

`E`에서 빈 타일을 4방향 플러드필한다. **닿지 않은 빈 타일은 전부 벽으로 메운다.**

- 확률 타일이 방 안에서 굴러 만든 밀봉 공동까지 같이 사라진다. 통짜 암반이 되는 것.
- `X`에 닿지 않으면 **생성 실패(에러)**. 원설계 §9의 연결성 검증을 이 단계가 겸한다.
- 메운 칸 수는 경고가 아니라 정보 로그로 남긴다(정상 동작이라 매번 뜬다).

**한계** — 4방향 연결만 본다. "뚫려는 있는데 점프로 못 닿는" 공간은 못 잡는다.
천장에 1칸 구멍만 난 공동 같은 것. 물리 시뮬레이션 없이는 판정할 수 없어 눈으로 확인한다(원설계 §1 범위 밖).

## 6. 프리셋 변경

| 제거 | 이유 |
|---|---|
| `gridWidth` / `gridHeight` | 마스크가 격자 크기를 결정한다 |
| `horizontalChance` | 워커가 없어졌다 |
| `loopChance` / `maxLoops` | 추가 연결이 대신한다 |

| 추가 | |
|---|---|
| `List<TextAsset> shapeFiles` | 형태 마스크 파일들 |
| `float extraConnectionChance = 0.25f` | 스패닝 트리 위에 얹을 추가 연결 비율 |

나머지(`roomWidth`/`roomHeight`, `roomTemplateFiles`, 심볼, `chanceTiles`, `objectSlots`, 보상,
`forceCarveBoundaries`)는 그대로다.

`DungeonRoomFiller.Fill`에서 `plan` 파라미터가 필요 없어진다 — FILL 방 보상 제외 규칙이 사라졌기 때문이다.
암반 칸에는 방이 없으니 보상 후보도 없다.

## 9. 위험

| 위험 | 대응 |
|---|---|
| 던전이 커진다 — 모든 칸이 방이라 지금(경로 10칸)보다 넓다 | 기본 마스크를 작게 잡는다. 5×3이면 52×20 타일. 형태별 weight로 조절 |
| 지도 없는 미로는 방황이 된다 (던전 안 미니맵은 `NO SIGNAL`) | 우선 크기로 조절하고, 실제로 돌아본 뒤 나쁘면 출구 방향 힌트를 따로 논의 |
| 점프로 못 닿는 공간은 메우기가 못 잡는다 | 눈으로 확인. `U` 방 발판 사다리 규약이 세로 이동만은 보장한다 |
| 템플릿 15종 × 변형 = 저작량 증가 | 자주 나오는 조합만 여러 장, 나머지는 1장으로 시작 |
| 기존 시드가 또 달라진다 | `Generated/`에 리팩터링 이전 산출물 2개(`gen_1764646830.txt`, `gen_1815610087.txt`)가 남아 있다. **새 파이프라인으로는 재현되지 않는다**(형태 마스크·미로 배선·E/X 후처리가 전부 바뀌었다). 참고용으로 두되 시드로 되살릴 수 있다고 기대하지 말 것 |

## 10. 범위 밖

- 런타임 생성 — 여전히 에디터 전용. 생성기는 `UnityEditor`를 참조하지 않는다.
- 점프 도달성 물리 검증.
- 링크 ID 재배정(`DungeonLinkRemapper`, 원설계 §8) — 템플릿 `[LINKS]`가 아직 전부 비어 있다.
  압력판·문을 템플릿에 넣는 순간 먼저 필요해진다.
